# Как выкатить и откатить wb-template-generator

> Операторская карточка: минимум, который нужен в момент выката или аварии.
> Почему всё устроено именно так — в стандарте деплоя.

Конкретные адреса не хранятся в репозитории: они лежат в секретах среды `production`
(`DEPLOY_HOST`, `DEPLOY_DIR`, `PROD_URL`) — смотреть в **Settings → Environments → production**.

## 🚀 Выкатить

1. Смержи PR в `main` (squash) — выкат едет **сам**: сборка образа по git-SHA → сторож свежести → выкат → smoke → запись в журнал.
2. Следи: **Actions → push_master**. Зелёный прогон = версия в проде и записана в журнал.

Выкатить **конкретную старую версию** (не HEAD): Actions → **rollback → Run workflow**, в `target` — полный 40-символьный SHA. Откат и «выкат старого» — один механизм.

## ↩️ Откатить

1. **Actions → rollback → Run workflow.**
2. `target` **пустой** = откат на предыдущую успешную версию из журнала (обычный случай).
3. Если workflow остановился с ошибкой **«диапазон отката содержит миграции БД»** — старый код может не работать с новой схемой. Убедись, что схема совместима (правило N−1), и перезапусти с галкой **`confirm_migrations`**.

Откат не требует ничьего согласования — жми и откатывай, разберёмся потом.

## 🔥 Если упало

| Симптом | Куда смотреть |
|---|---|
| Красный шаг **deploy** | лог шага; прод, скорее всего, остался на старой версии (или уже вернулся авто-откатом) |
| Красный шаг **smoke** | сработал авто-возврат на последнюю хорошую; проверь журнал и лог smoke — что именно не ответило |
| «Что сейчас в проде?» | репозиторий → **Environments → production** (журнал выкатов) или `<PROD_URL>/api/status` (поле `revision` = git-SHA) |
| Сервис молчит, выкатов не было | это не про выкат: смотри логи контейнеров на сервере (`docker compose -f docker-compose.deploy.yml logs`) |

## 🧯 GitHub недоступен (break-glass)

0. **Озвучь и получи добро руководителя** (в остром инциденте — озвучь постфактум). Записывать ничего не надо — след оставит механизм.
1. `ssh <DEPLOY_HOST>`, каталог `<DEPLOY_DIR>` (по умолчанию `/srv/wb-template-generator`).
2. Цель отката: `cat last-good-sha.prev` — если беда проявилась после успешного выката; `cat last-good-sha` — если текущий выкат не дошёл до конца.
3. Выкат — **предпочтительно тем же скриптом** (он сам запишет след в журнал хоста и возьмёт compose из git того же коммита):
   ```bash
   DEPLOY_HOST=<user@host> DEPLOY_DIR=<dir> ci/shell/deploy.sh <sha>   # со своей машины, из клона репо
   ```
   Крайний случай — сырыми командами на сервере (compose-файл там останется от прошлого выката):
   ```bash
   export DEPLOY_TAG=<sha> REGISTRY=ghcr.io/wirenboard
   docker compose -f docker-compose.deploy.yml pull
   docker compose -f docker-compose.deploy.yml up -d --wait
   ```
4. После инцидента — следующий выкат обычным путём (он же выровняет журнал конвейера).

## 👤 Контакты

- Владелец сервиса: заполнить при онбординге (строка сервиса в реестре продуктовых сервисов).
- Владение выкатом: **продуктовая команда** (сервис наш, инфра не участвует в выкате).
- Вопросы по стандарту: владелец стандарта деплоя.
