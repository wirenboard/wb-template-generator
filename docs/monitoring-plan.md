# План: мониторинг ресурсов и расходов LLM

## Контекст

Инцидент: пользователь увидел сырую ошибку OpenAI `429 insufficient_quota` при попытке анализа. Квота на серверном LLM-ключе исчерпалась.

Дополнительный фактор: на аккаунте OpenAI **не был включён auto-recharge** (автоматическое пополнение баланса). Если бы он был включён, OpenAI сам бы списал с карты при достижении порога. Но это лечит симптом, а не корень: без мониторинга админ не знает о расходах вообще, а auto-recharge может привести к неконтролируемому списанию при всплеске нагрузки или абьюзе.

## Что плохо сейчас

1. **Пользователь видит сырой JSON** от OpenAI — некрасиво и непонятно
2. **Админ узнал об исчерпании квоты от пользователя** — а должен был узнать заранее
3. **Нет истории расходов токенов** — непонятно, был ли всплеск или плавный рост
4. **Метрики `_metrics` есть, но почти не используются** — нет токенов, нет cost, нет алертов

## Что можно мониторить

### LLM-расходы
В `_call_llm` уже логируются токены каждого запроса:
```
Токены: prompt=X, completion=Y, total=Z
```
Уходит в логи и теряется. Нужно агрегировать:
- Сумма токенов за день/час по моделям
- Оценка стоимости по прайсу
- Алерт при превышении порога

### Метрики `/api/metrics`
Уже есть `analyze_total`, `analyze_duration`, `rate_limit_hits`. Не хватает:
- `llm_tokens_total` (prompt/completion отдельно)
- `llm_errors_total` по типам (quota, network, parse, validation)
- `llm_cost_estimate_usd` (оценка по прайсу модели)

### Внешний мониторинг
- **Простое**: cron на сервере раз в час дёргает `/api/metrics`, шлёт в Telegram если расход скакнул
- **Среднее**: Prometheus exporter + Grafana dashboard
- **Сложное**: интеграция с Sentry для алертов по ошибкам

### UI/UX
Маппинг известных ошибок LLM на человекочитаемые сообщения:
- `insufficient_quota` → «Закончилась квота сервиса, попробуйте позже или используйте свой LLM»
- `rate_limit_exceeded` → «Слишком много запросов, попробуйте через минуту»
- `invalid_api_key` → «Неверный API-ключ»
- `model_not_found` → «Модель недоступна»

### Превентивные меры
- **Жёсткие лимиты**: уже есть rate limit по IP, но он защищает от спама, а не от расхода токенов. Можно добавить лимит токенов на IP в день
- **Mock-режим как fallback**: при достижении порога расходов автоматом переключаться в `mock_data.py` вместо LLM
- **Per-user квоты**: требует авторизации, отложить

## Приоритеты

### P0 — критично, 1-2 часа работы
1. Маппинг типичных LLM-ошибок на понятные сообщения в UI
2. Добавить токены и cost estimate в `/api/metrics`

### P1 — полдня
3. Простой сборщик расходов по дням в JSON-файле + ручка `/api/usage` (защищённая basic auth или ключом)
4. Алерт через webhook (Telegram/Slack) когда дневной расход > порога

### P2 — день+
5. Prometheus endpoint + готовый Grafana dashboard
6. История запросов с request_id и токенами в SQLite

### P3 — когда захочется
7. Per-user квоты с авторизацией
8. Sentry интеграция
9. Mock fallback при исчерпании квоты

## Открытые вопросы

- Где админ должен видеть метрики? (отдельная страница в UI / Grafana / Telegram-бот / только логи)
- Кто платит за токены — есть ли понимание дневного бюджета?
- Нужна ли авторизация для админских ручек или достаточно отдельного порта/IP whitelist?
- Включать ли auto-recharge в OpenAI как страховку, или принципиально нет (контроль расходов)?
